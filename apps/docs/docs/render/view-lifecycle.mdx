# Manage view lifecycle

A `NotebookView` moves through three states, tracked by two gates.

| State                   | `has_rendered` | `has_graph_snapshot` | Available readback                          |
| ----------------------- | -------------- | -------------------- | ------------------------------------------- |
| Created                 | `False`        | `False`              | View selection                              |
| Graph synchronized      | `False`        | `True`               | Graph metadata                              |
| Selected cells rendered | `True`         | `True`               | Values, per-cell values, and graph metadata |

Reading synchronized state before the required gate raises
[`NotRenderedError`](../reference/values-and-graph.mdx#notrenderederror).
The gates are view-local: rendering one view leaves a newly created sibling
unreadable until that sibling renders.

```python
if full_view.has_rendered:
    values = full_view.runtime_values

if full_view.has_graph_snapshot:
    graph = full_view.graph
```

## Mounting and remounting

Browser evaluation starts when an anywidget host mounts the view. A
`NotebookView` owns one live writable output at a time:

- The same view can render again after its previous output is torn down, for
  example when a marimo cell reruns.
- When the same selection must appear in two outputs simultaneously, create
  one view per placement. See [Display a
  NotebookView](display-views.mdx#one-view-per-placement).

## Rebuilds reset the gates

`replace_variables` and `reset_variables` release Python-owned names back to
their notebook definitions. That requires rebuilding each active runtime, so
both gates clear until the replacement graph and render snapshots
synchronize. `update_variables` patches values in place and does not rebuild.

Previously synchronized readback is invalidated by the rebuild; wait for the
gates again before reading.

## Closing

```python
readout_view.close()   # closes one view
notebook.close()       # closes the session and every view created from it
```

`NotebookView.close()` disposes that view's browser runtime, model listeners,
and DOM. Other views from the notebook remain active. Repeated calls are
no-ops, and previously synchronized readback remains readable. Variable
mutators on a closed view raise `RuntimeError`.

`Notebook.close()` closes the session and every live view. After closing,
creating views, changing variables, or assigning a theme raises
`RuntimeError`. Construction-time metadata such as `spec`, `source`, and
`attachments` remains readable.

Views are also tracked weakly: a view that goes out of scope without
`close()` does not keep the notebook session alive.

## Resource cleanup inside cells

Cells that own browser resources should release them through Observable's
`invalidation` promise, which resolves when the cell is invalidated or its
runtime is disposed:

```python
obs.js(
    """
    const controller = new AbortController();
    invalidation.then(() => controller.abort());

    const response = await fetch(dataUrl, {signal: controller.signal});
    const records = await response.json();
    """
)
```

See [Browser execution and network
access](../customize/browser-execution.mdx#promises-generators-and-invalidation)
for how the runtime tracks asynchronous values.
