# Bidirectional inputs

When a Python variable shares its name with a named `viewof` input, the two
sides negotiate one value. The Python value seeds the control, browser
interactions become shared session state, and a later Python update takes
the name back.

Drag either control. The marimo slider asserts the value from Python. The
Observable input changes it from the browser. The readout follows
whichever side acted last.

## The negotiation, step by step

1. **Seed.** At construction, the Python value `gain=5` seeds the `viewof`
   control and takes precedence over the source default.
2. **Browser interaction.** Dragging the Observable input makes its value
   shared session state. Sibling views that render an input with the same
   name receive the value, and readback reports it to Python.
3. **Python reasserts.** An `update_variables` call that includes the name
   clears the interacted state and applies the Python value to every active
   view. This also reasserts a Python value that has not changed in Python,
   which is why moving the marimo slider back to its old position still
   resets the browser control.
4. **Release.** Removing the name through `replace_variables` or
   `reset_variables` restores the source-defined input default.

## Which values can be shared

Shared input state accepts `null`, booleans, strings, numbers including
special numeric values, `BigInt`, valid dates, arrays, plain objects, maps,
and sets, with containers checked recursively. Values such as functions, DOM
elements, files, and binary buffers remain local to the view that produced
them. Use the same input type for a shared name across views: a mismatched
target can coerce an incompatible value before the round-trip check
suppresses its events.

The precise contract is in [Variables and
serialization](../reference/variables-and-serialization.mdx#python-values-and-viewof-inputs).
